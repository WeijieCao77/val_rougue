# 在线服务扩容：SQLite 存储、进度同步与压测（2026-09-27）

目标：为玩家可能增长到 1000 人以上做准备。只用 Node 24 自带能力，不加 npm 依赖，也不加付费的 Railway 服务。

## 一、架构变化

### 之前
- 生产环境（Railway，服务 Val_Rogue，`DATA_DIR=/data` 持久卷，没有 `DATABASE_URL`）使用 `online/store.mjs` 里的 FileStore。
- 全部在线数据（账户、云端构筑、房间、对局、幂等记录）是**一份** `online-data.json`。
- **每个请求**都在同一把锁下执行一次事务，包括只读的房间轮询：深拷贝整份数据、序列化比较、有改动时整份重写文件。
- 数据越多，每次请求越慢；所有请求都只能排队通过这一把锁。
- 备用的 PgStore 也一样：一行 JSONB 加 `FOR UPDATE`，同样是全局串行。

### 现在
- 存储改为 `online/sqlite-store.mjs`，底层是 Node 24 自带的 `node:sqlite`（`DatabaseSync`）。
- 数据库文件是 `${DATA_DIR}/online.db`，开启 WAL、`synchronous=NORMAL`、`busy_timeout=5000`、外键约束。
- 数据分表存放：

  | 表 | 内容 | 主键／索引 |
  | --- | --- | --- |
  | `accounts` | 账户 | 主键 `account_id`；唯一索引 `token_hash`；索引 `room_code` |
  | `archives` | 云端构筑 | `(account_id, pos)` |
  | `checkpoints` | 已处理的检查点（幂等） | `(account_id, checkpoint_id)` |
  | `rooms` | 房间与对局 | 主键 `code`；索引 `(status, last_action_at)` |
  | `room_requests` | 对局动作的幂等记录 | `(room_code, request_key)` |
  | `sync_links`、`sync_codes` | 进度同步 | — |
  | `meta` | 迁移记录 | — |

- `online/api.mjs` 的接口行为和返回格式完全不变，只把存储调用换成了窄接口：
  - `store.getAccountByTokenHash()` 是一次索引查询；
  - `store.tx(t => …)` 是一个短小的**同步**工作单元，按需读取 `t.account`、`t.room`、`t.checkpoint`、`t.request`，提交时**只写回 JSON 真的变化了的行**。
- 因为 `node:sqlite` 是同步 API，而工作单元规定不能 `await`，事务执行期间不会插进别的请求，也就不再需要 JS 锁。
- 只读请求（房间轮询、读取账户）不写库。回合计时到期属于真实状态变化，仍会在轮询时写入（已有测试覆盖）。
- 房间清理每小时一次：结束超过 7 天的房间、两天无人操作的等待中／对战中房间会被删除，相关账户同时释放。
- 限流仍在内存里（单实例足够）。
  - 新增：在 Railway 上（或 `TRUST_PROXY=1`）按 `X-Real-IP`，或 `X-Forwarded-For` 的最后一跳，识别玩家 IP。
  - 之前所有请求都来自 Railway 代理地址，"每 IP 每分钟 30 次注册"实际上是全站共用一个额度。
- `node:sqlite` 加载时会打印一条 ExperimentalWarning。代码只在导入那一刻过滤这一条，其他警告不受影响。
- PgStore、`DATABASE_URL` 路径和 `postgres` 依赖都已删除。设置了 `DATABASE_URL` 只会在日志里提示"已不再使用"。

### 进度同步（新功能，同一个数据库）
- `/api/sync/code|redeem|sync|restore`，瓦 Demo 与新 Demo 分开同步。
- 同步码：6 位，使用无歧义字符，10 分钟内一次性有效。
- 安全：每台设备有自己的密钥，服务端只存 sha256。
- 进度包：上限 512 KB（未压缩），服务端 gzip 后存储，实测压缩到 5–10%。
- 冲突处理：版本号单调递增；两台设备都改过时，保存时间较晚的一份胜出，另一份存为单槽备份，可以恢复。
- 自动清理：过期同步码，以及 180 天无人使用的同步组。
- 客户端 `shared/progress-sync.js`：
  - 最多每 30 秒上传一次；幕结束、局结束和页面隐藏时会立即上传；
  - 打开游戏时检查另一台设备的进度，较新就采用，并提示"已同步另一台设备的进度（x 分钟前）"。

## 二、迁移与回滚

### 迁移（自动，首次用新版本启动时）
1. 如果 `DATA_DIR` 里有 `online-data.json`，就在**一个 SQLite 事务**里整体导入。
2. 核对账户、存档、检查点、房间、幂等记录的条数，一项对不上就整体回滚、启动失败。原文件不动。
3. 在 `meta` 表记下原文件的 sha256，然后把原文件**改名**为 `online-data.migrated-<时间>.json` 保留，**不删除**。
4. 重复启动是幂等的：
   - 提交后、改名前崩溃：下次看到同一 sha256，只改名，不重复导入。
   - 迁移完成后又出现一份不同的 `online-data.json`：不合并，只在日志里警告。
5. 测试 `tests/online-store.test.mjs` 用旧 FileStore 真实生成的数据（`tests/fixtures/legacy-online-data.json`：4 个账户、9 个存档、1 个已核验检查点、1 个进行中房间、1 个已结束房间）逐项核对，包括：
   - 迁移后原来的令牌能登录；
   - 进行中的对局能继续；
   - 迁移前的幂等请求 ID 仍然有效；
   - 已领取的检查点不会重复入库。

### 回滚到旧版本（只在必要时）
1. 先导出迁移之后产生的新数据。在 Railway 的服务 shell 里运行：
   `node tools/export-online-json.mjs /data /data/online-data.json`
   服务运行时也可以导出（WAL 读不阻塞写）。
2. 在 Railway 上重新部署旧提交（例如 `3548bef`）。旧代码读取 `/data/online-data.json`。
3. 如果不需要迁移后的新数据，也可以直接把 `online-data.migrated-*.json` 改名回 `online-data.json`。
4. 回滚会丢失进度同步数据（旧版本没有这个功能），玩家本机进度不受影响。
5. 之后再升级：新代码看到的 `online-data.json` 与已迁移文件的 sha256 不同，会**跳过并警告**，不会覆盖数据库。这时需要先删除或改名 `online.db*`，再让它重新导入。

## 三、压测（仅本机，从未对线上）

工具是 `tools/loadtest.mjs`：
- 自己启动一个本地服务器，用临时 `DATA_DIR`，设 `TRUST_PROXY=1`，每个模拟玩家带独立的 `X-Real-IP`；
- 服务器进程内有一个探针，每秒通过 IPC 报告 RSS 和 CPU。

测试机与条件：
- Windows 11 笔记本，Node 24.14；
- 服务器与压测客户端在**同一台机器**上，客户端本身也在占用 CPU（它要生成 100–250 KB 的同步包）；
- 所以下面的延迟偏保守，服务器 CPU 占用才是更可靠的指标。

### 3.1 全量场景（新 SQLite 存储）
场景配置：
- 1000 个账户；
- 300 次真实的爬塔核验领取：`rules4-claim.json`，一整幕、283 个动作；
- 100 场并发 PvP，200 名玩家各每秒轮询 1 次，轮到自己时约每 2.5 秒行动一次；
- 300 名玩家各有 100–250 KB 的进度包，每 30 秒自动同步一次；
- 稳定阶段持续 180 秒。

| 接口 | 次数 | p50 ms | p95 ms | p99 ms | 错误 |
| --- | ---: | ---: | ---: | ---: | ---: |
| POST /api/account | 1000 | 10.1 | 31.3 | 46.7 | 0 |
| POST /api/archive/claim | 300 | 5067 | 6344 | 6467 | 0 |
| GET /api/account（领取期间） | 300 | 1256 | 2437 | 2477 | 0 |
| POST /api/rooms、join、ready | 400 | 4 | 7–14 | 8–14 | 0 |
| GET /api/rooms/:code（轮询） | 34695 | 44.3 | 153.9 | 208.8 | 0 |
| POST /api/rooms/:code/action | 11600 | 70.8 | 201 | 256.7 | 0 |
| POST /api/sync/code | 300 | 8.7 | 84.6 | 130 | 0 |
| POST /api/sync/sync（上传） | 1500 | 32.9 | 133.7 | 189.3 | 0 |

- **错误率 0%**，共 1500 次同步上传、11600 个对局动作。
- 稳定阶段 266 请求/秒。
- 服务器 CPU：平均 **20.6%**，最高 41.5%（按单核计）。
- 服务器内存：RSS 平均 228 MB，峰值 **242 MB**。
- 领取阶段 CPU 持续约 100%，吞吐 **2.48 次领取/秒**。
- 数据库（含 WAL）12.7 MB：1000 个账户、300 个存档、300 个同步组，加上房间。
- 稳定阶段服务器只用了约 1/5 个核，轮询的 44 ms 中位延迟主要来自同机压测客户端的排队。下面的小场景可以对照：负载较轻时，同一接口 p50 只有 1.7 ms。

### 3.2 新旧存储对比（小场景，相同脚本）
场景：200 个账户、60 次领取、30 场 PvP（60 人每秒轮询）、60 秒，不测同步（旧版没有这个功能）。
旧版本来自 `3548bef` 的 `online/api.mjs` 与 `store.mjs`，只改了限流取 IP 的一行，让每个模拟玩家有独立 IP。

| 指标 | 旧 FileStore（整份 JSON） | 新 SQLite |
| --- | ---: | ---: |
| 轮询 GET /rooms/:code p50 / p95 / p99 | 449 / 1170 / 1353 ms | **1.7 / 4.0 / 5.4 ms** |
| 行动 POST action p50 / p99 | 847 / 1915 ms | **2.2 / 9.2 ms** |
| 建房／加入／准备 p50 | 79 / 91 / 144 ms | 5.4 / 5.9 / 5.2 ms |
| 稳定阶段服务器 CPU | **91.6%（已饱和）** | 5.0% |
| 60 秒内完成的对局动作 | 1083 | 1200 |
| RSS 峰值 | 294 MB | 205 MB |

- 旧存储在只有 60 名在线对战玩家、数据文件才 0.6 MB 时就已把单核跑满。
- 原因是每次轮询都要深拷贝并序列化整份数据；数据越多越慢，所以 1000 名玩家时根本撑不住。
- 新存储每个请求只碰自己需要的几行，耗时与总玩家数基本无关。

复现命令：
```
node tools/loadtest.mjs --players 1000 --claims 300 --matches 100 --syncers 300 --duration 180
node tools/loadtest.mjs --players 200 --claims 60 --matches 30 --syncers 0 --duration 60 --server <旧版 server 入口>
```

## 四、单实例容量估算

依据：稳定阶段 266 请求/秒只用了约 0.2 个核，每请求约 0.8 ms CPU；单核按 80% 可用计，约 1000 请求/秒。

- **PvP**：每场约 2.4 请求/秒（双方每秒轮询加上行动）。CPU 上限约 300 场同时进行（600 人同时对战）。保守按 **150–200 场同时对战** 规划。
- **进度同步**：每名在线玩家约 1 次／30 秒。1000 名同时在线约 33 请求/秒，负担很小。
- **注册、读取账户、建房**：毫秒级，不是瓶颈。
- **爬塔核验领取是主要瓶颈**：
  - 每次领取要在主线程完整重放一幕，约 0.3–0.4 秒 CPU；
  - 单实例上限约 2.5 次/秒（约 9000 次/小时）；
  - 重放期间每 100 个动作让出一次事件循环，同时段其他请求会被拖慢到秒级（见上表领取期间的 GET /api/account）。
  - 1000 名注册玩家通常每分钟只有几次领取，影响有限。但如果大量玩家同时打完一幕，PvP 轮询会短暂变慢。
- **内存**：约 200–250 MB，与玩家数关系不大。房间 JSON 与同步包都存在磁盘上，不驻留内存。
- **磁盘**：每名玩家约 5–15 KB 账户与构筑数据，每个同步组约 10–25 KB（gzip 后）。1000 名玩家不到 50 MB。
- **结论**：单个 Railway 实例（1 vCPU 以内、512 MB 内存）足以支撑约 **1000 名注册玩家**、**100–200 名同时在线**、**数十到一两百场同时 PvP**。

## 六、剩余瓶颈与建议

1. **核验重放占用主线程**（最大的瓶颈）：
   - 把 `rebuildSnapshot` 放进 `worker_threads` 线程池（2–4 个 worker），主线程只做 I/O 与短事务，轮询就不会被领取拖慢。
   - 其次可以优化 `waAct` 每步的整状态拷贝。
2. **静态资源不缓存、不压缩**：
   - 为 `app.js`、CSS、图片加 `ETag`，并用带版本号的 URL 配合长缓存；
   - 用 `node:zlib` 做 gzip 或 brotli 预压缩。
   - 能明显降低出站流量和手机加载时间。这是影响费用的最大一项。
3. **PvP 轮询**：
   - 每秒一次完整视图。可以改为"带上已知 rev，服务端在没有变化时返回 304 或极简响应"，或者长轮询。
   - 能把对局流量减少一个数量级。
4. **单实例**：
   - SQLite 只允许一个进程写，Railway 副本数必须保持 1。
   - 超过单机能力（大约同时在线数千人）时，再考虑换成真正的 Postgres 按行存储（表结构可以直接照搬），或者把 PvP 拆成独立服务。
5. **备份**：
   - Railway 卷本身不等于备份。
   - 建议定期运行 `tools/export-online-json.mjs`，或用 `VACUUM INTO` 做快照，然后复制到别处。
6. **限流在内存中**：重启后清零。单实例下可以接受。

## 七、2026-09-27 补记：核验线程池与静态资源缓存压缩

第六节的第 1、2 条已完成。第 3–6 条不变。

### 7.1 爬塔核验移出主线程
- 核验代码从 `online/api.mjs` 原样搬到 `online/claim-verify.mjs`（`verifyClaim(run, act)`），没有改动逻辑。进程内路径与线程池共用这一份代码。
- `online/replay-pool.mjs` 是基于 `node:worker_threads` 的线程池，不加依赖；`online/replay-worker.mjs` 是线程入口。
  - 线程数：min(可用 CPU − 1, 4)，至少 1 个。有任务时才启动线程，空闲 60 秒后关闭，不占内存。
  - 队列上限 50：所有线程都在忙、队列也满时，立即返回 **503「服务器繁忙，请稍后再试」**，带 `Retry-After: 5`。
  - 单个任务超时 15 秒（一幕约 280 个动作，重放约 0.4 秒；三幕完整记录也远低于 15 秒）：终止该线程并换新，返回同样的 503。
  - 线程崩溃：换新线程，该任务按"意外异常"处理，返回 500「服务器内部错误」，与以前进程内出异常时一样。
  - 每个线程堆上限 256 MB（`resourceLimits`）。
- 线程只收到纯 JSON（run 和 act），返回核验后的快照，或 HttpError 的状态码和消息。写库仍在主线程，放在一个短事务里。
- 返回内容逐字节不变：测试把 6 个规则／经济版本的真实记录，加上篡改、缺检查点、非法版本等情况，分别用进程内和线程池各跑一遍，结果完全相同；用两种方式走完整个接口，响应和入库的快照也完全相同。
- `createOnlineHandler(store, { verifyClaim })` 可以注入核验函数。测试默认用进程内方式（快、确定），`server.mjs` 注入线程池。
- 关闭：收到 SIGTERM（Railway 部署时发送）后停止接新连接，进行中的请求完成后终止所有线程；仍在排队的请求返回 503，客户端保留凭证，之后会重试。
- 线程文件不在静态白名单里，浏览器请求返回 404（有测试）。

### 7.2 静态资源：缓存与压缩（`static-cache.mjs`）
- 压缩：文本类型（html、js、css、json、svg、gltf）在客户端支持时返回 brotli（质量 11），否则 gzip（级别 9）。
  - 按"文件 + 修改时间 + 大小"只压缩一次，结果缓存在内存里（只缓存白名单里的文本文件，原文加压缩结果共几 MB；图片和模型只缓存 ETag，不缓存内容）。服务器启动后在后台预先压缩白名单里的文件。
  - 小于 1 KB 的文件和已经压缩过的格式（png、jpg、webp、glb）原样发送。
  - 压缩响应带 `Vary: Accept-Encoding`。
- 缓存校验：`ETag` 用文件内容的 sha1（弱 ETag，各种编码共用），外加 `Last-Modified`。`If-None-Match`／`If-Modified-Since` 命中时返回 304，不带正文。内容没变的文件在重新部署后 ETag 不变，玩家仍然只收到 304。
- `Cache-Control`：
  - HTML 入口页、JS、CSS、JSON、gltf：`no-cache`（每次都向服务器确认，新版本上线后立即生效；没变就是 304）。ES 模块按固定路径互相导入，URL 没有版本号，所以不能长缓存。
  - 图片（`/assets/` 下的照片与图标、两张封面）和 `.glb` 模型：`public, max-age=604800`（一周）。
    - 取舍：如果替换了同名图片，已经缓存的浏览器最多一周后才会看到新图。这类文件很少替换，可以接受。
    - 没有给图片 URL 加 `?v=`：图片路径分散在 `app.js`、`art-data.js` 等生成代码里，加版本号要改构建流程，收益不大。以后真要替换照片，换一个文件名即可。
  - API、`/healthz`、`/runtime-config.js`、404 等仍是 `no-store`。
- 白名单与安全头（`X-Content-Type-Options: nosniff`）不变；HEAD 可用；不支持 Range。
- 补充：线上 Railway 边缘节点本来就会对文本做 gzip（线上 `app.js` 实测 760 KB 压到 202 KB）。所以对玩家来说，冷加载的改进主要来自 brotli（比 gzip 再小约 13%）；**更大的改进是重复打开时的 304**，以前每次都是 `no-store` 全量下载。

### 7.3 流量实测（本机，字节数含响应头）
页面资源清单来自浏览器实际加载的封面页：瓦 Demo 7 个文件，新 Demo 58 个文件，都不含进入对局后才加载的照片和模型。

| 页面 | 以前（源站原文） | 以前（经 Railway 边缘 gzip） | 现在冷加载（brotli） | 以前重复打开 | 现在重复打开 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首页 `/` | 417 KB | 415 KB | 415 KB | 415 KB | **0.3 KB**（封面图走本地缓存） |
| 瓦 Demo `/wa/` | 1802 KB | 638 KB | **555 KB** | 638 KB | **1.6 KB**（5 个 304 + 1 个 no-store 小脚本，封面走缓存） |
| 新 Demo `/new/` | 1844 KB | 642 KB | **567 KB** | 642 KB | **15 KB**（57 个 304，封面走缓存） |

- 源站出站：冷加载减少约 69%，重复打开减少 99% 以上。
- 玩家侧：冷加载比以前（边缘 gzip）再少约 13%；重复打开从约 640 KB 降到几 KB。
- 第五节估算的"静态资源流量约 20–50 GB/月"中，大部分来自重复打开，预计降到原来的五分之一以下。

### 7.4 压测：领取与 PvP 轮询混合（本机）
场景：`node tools/loadtest.mjs --players 300 --claims 200 --matches 100 --syncers 0 --duration 60 --steady-claims 5`
- 先连续领取 200 次（16 路并发），然后开 100 场 PvP（200 人每秒轮询 1 次）。
- 稳定阶段 60 秒内，每隔 10 秒插入一段 10 秒的领取高峰，每秒 5 次（最多 16 个同时进行）。
- 机器：8 个逻辑核的 Windows 笔记本，线程池 4 个线程；压测客户端在同一台机器上。

| 指标 | 以前（主线程重放） | 现在（线程池） |
| --- | ---: | ---: |
| 轮询 GET /rooms/:code p50 / p95 / p99（整个稳定阶段） | 218 / 3187 / 3608 ms | **2.1 / 5.8 / 8.5 ms** |
| 轮询 p50 / p95 / p99（仅领取高峰期间） | 1166 / 3470 / 3641 ms | **1.8 / 4.4 / 5.9 ms** |
| 对局动作 POST action p50 / p99 | 493 / 3594 ms | **3.9 / 17 ms** |
| 领取期间 GET /api/account p50 / p99 | 1236 / 2478 ms | **0.7 / 1.4 ms** |
| 批量领取吞吐 | 2.48 次/秒 | **8.83 次/秒** |
| 批量领取 p50（16 路并发排队） | 5038 ms | 1749 ms |
| 高峰期领取 p50 / p99 | 4864 / 6532 ms | **426 / 658 ms** |
| 60 秒内完成的对局动作 | 2728 | 4000（满额） |
| 错误 | 0（另有 1 次客户端超时） | 0 |
| 服务器 RSS 峰值 | 211 MB | 714 MB（4 个线程同时满载） |
| 服务器 CPU（稳定阶段，按单核计） | 70.6% | 131.7%（重放分到多个核上） |

- 领取不再拖慢任何其他请求。即使服务器只有 1 个核，轮询也会和重放线程由操作系统分时调度，不会再出现以前一次重放卡住整条事件循环的秒级停顿。
- 内存：每个忙碌线程约 100–120 MB。只在领取高峰期间存在，空闲 60 秒后释放，平时 RSS 与以前相同（约 200–250 MB）。
  - 如果 Railway 上内存确实紧张，可以在 `server.mjs` 里把线程数调小（`createReplayPool({ size: 1 })`），主线程仍然不会被阻塞，只是高峰期领取排队更久。

### 7.5 部署
- 不需要改 Railway 配置，也不需要新的环境变量；只用 Node 24 自带模块。
- 上线后可以核对：`curl -sI -H 'Accept-Encoding: br' https://valrougue-production.up.railway.app/app.js`，应看到 `etag` 和 `cache-control: no-cache`，以及 `content-encoding: br`（前提是 Railway 边缘节点原样转发已压缩的响应；若边缘改写了编码，ETag 和 304 仍然有效）。
