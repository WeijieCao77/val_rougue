## 已有 PvP 与本作新增部分

查到的好友对战流程是：输入好友对战码 → 服务端返回好友保存的五人阵容 → 本机调用 `playRivalMatch` 模拟比赛 → 保存友谊赛记录。对方无需同时在线。这是**玩家构筑之间的异步对战**。源码明确说明了这个目标，并由调用路径印证：[噜噜卡 Friends.tsx 第27行起及第74行](https://github.com/WeijieCao77/lulu_card/blob/f121b054627fb7fa1d5dc825e030c0bd50a943ef/src/ui/cards/Friends.tsx#L27)、[开瓦包对应入口](https://github.com/WeijieCao77/Val_Manager/blob/b0f2d3cbf6d17ca3c22e7a3a039be787b012f595/src/ui/cards/Friends.tsx#L27)。

不能因此把上述好友赛误称为全程服务端结算；其他有收益操作的服务端执行路径是另一项已存在能力。也不能由这两个入口推断整个仓库绝无其他联机机制。

本作已确认的是**双方玩家亲自出牌**。需要补充的主要是：

1. **历史构筑领域数据**：大关奖励后按自身最大血量回满，保存永久牌组与被动；10个跨局共享槽位，满位主动确认替换。当前局、历史库、进行中的对局分别保存。
2. **双人规则引擎**：定义回合顺序、状态时点、抽弃消耗、胜负、先后手及退出规则。以本作卡牌结算为基础，不移植旧模拟器的比赛数值。
3. **好友房间与命令接口**：创建、加入、双方准备、锁定同幕兼容构筑、出牌、结束回合、退出、重连；每个动作带唯一请求号和对局版本。选择轮询、长轮询或 WebSocket 是实现选择，不必先做大型实时平台。
4. **信息隔离与恢复**：服务器持有完整状态与私有随机源，只发送对应玩家可见的手牌、公开信息和事件；不能把双方全状态发到浏览器后仅靠界面隐藏。保存到足以在服务重启后恢复或明确终止对局的程度，不能无声丢局。
5. **构筑可信来源**：服务端保存一个客户端上传的对象，并不证明它合法通关。好友测试可显式标注未验证导入；可信构筑需由服务端产生或核验其过程。记录必要动作便于重连和排错，完整回放界面不作为首期硬依赖。

第1项与基础服务适配可并行于第2项的规则验证；规则稳定后接第3—4项。基础可信来源应随正式历史保存路径设计，没必要先上线再补所有数据来源定义。

## 对策划规模的实际影响

应把“云端历史库＋好友真人对战”作为明确的工程目标估算；不能因当前入口静态而默认退回只能导出文件或只能单机。浏览器 localStorage 可以承担缓存、未同步进度或离线原型，而不必承担永久历史库的唯一副本。跨设备恢复体验仍需确定，不把代码可行性误写成已经上线的产品承诺。

已有基础也不意味着应一次搬入抽卡商城、交易市场、天梯、全服杯和公会。当前核心仍是：**75张完整牌池的爬塔构筑 → 10槽历史库 → 同幕好友真人打牌**。复用代码模块与经验，不默认连接或修改旧游戏生产库；新玩法规则、素材和数据结构独立评审。

最小验收包括：两浏览器分别登录并打完一场；不泄露对方手牌与牌序；重复请求不多出牌；并发结束回合只成功一次；旧客户端不能覆盖新状态；满10槽替换失败保住旧卡组；新开爬塔仍能找到历史库；中途替换历史卡组不影响已锁定对局；断线和服务重启后的状态有明确结果。不能仅凭单人本机演示宣称联机完成。
