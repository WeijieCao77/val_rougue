# 爬塔构筑、历史卡组库与独立PvP模式（方案，未实现）

## 用户提出的机制

每完成一个大关，保存当时的卡组与数据；完成一幕的存档与一幕存档对战，二幕与二幕对战，三幕与三幕对战。玩家继续肉鸽后，早期存档仍保持当时的构筑。PvP希望突出构筑、双方临场决策和受规则约束的运气。

用户进一步明确：爬塔与PvP本质上是两个独立模式。爬塔是类似故事模式的卡组构筑过程；大关结算产生的完整构筑进入长期历史卡组库，即使新开一局，玩家也能在PvP模式找到并使用旧卡组。首期采用双方玩家亲自操作的好友对战，先做房间码邀请，不做大型公共匹配系统或好友社交系统。

当前原版Demo及其冻结标签继续保留。本文件不表示已上线历史卡组库、联网或匹配。整回合/单动作交替等对战细则仍属待验证提案。

## 两个入口与历史卡组库

- **爬塔／故事模式**：新开一局、继续当前进度，在路线选择、奖励、升级等过程中形成构筑。大关结算后自动向历史卡组库追加一份完整构筑。
- **PvP／好友对战**：不要求存在正在进行的爬塔存档；可以直接浏览过去所有局的历史构筑，选择一份，再创建或加入房间。
- **历史卡组库**：独立于当前局保存。至少显示来源局、完成幕数、生成时间、牌数、升级情况、最大血量、遗物及兼容版本；支持查看完整牌表，建议提供命名、收藏与按幕数筛选。名称等展示信息可改，冻结的构筑内容不可因此改变。
- 新开一局、覆盖当前局、失败、通关、放弃当前进度，都不得清空或覆盖历史库。PvP结束不损耗历史构筑，也不要求重新爬塔才能再用。
- 例如第8局的一幕构筑、第12局的一幕构筑、第8局的二幕构筑可同时存在。玩家开始第20局后仍可选择它们；对战按所选构筑完成的幕数匹配，不按账号当前最高进度匹配。
- 版本变化不能静默删除历史卡组。若某规则不兼容，保留原始记录并说明可用模式；版本兼容政策需独立制定，不能承诺任意旧规则永久加入最新匹配池。

首期好友流程：进入PvP → 选择历史构筑 → 创建房间并分享房间码 → 好友加入并选择同幕、兼容规则的历史构筑 → 双方准备 → 独立对战 → 结算后回到PvP入口。不能在准备后无提示换卡组；若更换，取消准备并重新校验。不必建设好友列表、聊天或公共匹配队列。

好友对战仍需稳定的玩家识别与历史存储，但不意味着首期必须建设复杂账号系统。房间码用于加入对局，不充当访问整座私人历史库的身份凭证。历史库是否支持跨设备同步，当前未作用户承诺。

### 后续已确认的血量与金钱规则

用户明确：大关结束后单机也应回满血；最大血量来自成长选择与机会，属于构筑收益，必须完整保留。PvP继承各自存档的最大血量，并以各自上限满血开局，不统一、不取平均、不自动缩放补偿。金钱完整记录，当前没有PvP开局消费渠道，因此不参与对战结算，也不自动换成战斗加成。

设计评价要考虑提高最大血量所放弃的卡牌、升级或其他收益，不能单凭血量高就判定不公平；也不能未经测试假定每一种加上限机会都已付出了等价代价。

实现差异：核查旧Demo的engine.js，第一、二幕finishBossSkin当前仍仅恢复最大声望的30%，第三幕胜利没有统一回满步骤；这不是新约定的实现状态。本轮修正方案，未改动线上或冻结Demo。后续新版本应在大关奖励全部结算后回满血，再锁定快照。

## 保存规则建议

1. 第一、二幕击败Boss后，完成奖励选择或跳过，按结算后的最大血量回满，再自动锁定存档。三幕在冠军战胜利结算、回满后锁定。若奖励改变上限，先更新上限再回复，不按旧上限保存。
2. 同一玩家、runId、完成幕数与PvE规则版本只生成一份原始快照。重复刷新或继续下一幕不能覆盖、重复领取或升级早期存档。新一局产生新runId并向同一历史库追加新快照，不能替换上一局卡组。
3. 原始快照保存永久牌组实例、升级、永久负面牌、遗物效果标识、原始当前及最大声望、金钱、赛区、完成幕数、PvE版本与通关履历。界面可以展示最终战况，但它不作为竞技开局状态。
4. 竞技规则版本独立于PvE存档版本。新规则下转换入场数据不会改写原始存档；旧版本不兼容时明确提示，不静默套入新卡值。
5. 一份存档可重复对战。PvP输赢不扣除肉鸽声望、不消耗卡牌、不更改原赛季，也不通过奖励反向增强该存档。

## 保存数据与对战继承分开

| 数据 | 原始存档 | 建议的PvP开局 |
| --- | --- | --- |
| 永久卡牌、数量与升级 | 完整保存 | 继承；不在入场前任意增删重组 |
| 永久诅咒/负面卡 | 完整保存 | 初始建议继承，保留获取强力奖励时付出的代价 |
| 遗物及永久被动 | 完整保存 | 逐项检查兼容性；可用规则公开，不能悄悄失效 |
| 当前/最大声望 | 完整保存；大关结算后当前值等于各自上限 | 完整继承各自最大值，每场以各自上限满血开局；不统一上限、不因上限差异自动补偿 |
| 金钱 | 完整保存 | 首期只展示，不增加PvP商店或付费强化 |
| 本场已部署能力、布防、压制、易伤 | 可作为战况履历保留 | 清空；能力牌回到永久牌组，重新打出后才生效 |
| 手牌、抽弃消耗堆、临时生成卡 | 可作为战况履历保留 | 从永久牌组重新洗抽；不带临时卡与Boss战牌序 |

本项目skins目前含有实际被动效果，不只是外观。不能把它当作“纯展示、无平衡影响”全量带入，也不应另造bossRelics字段重复计入同一个效果。

## 匹配与真人对战

- 核心匹配键为完成幕数＋兼容的竞技规则版本。三幕玩家可使用自己锁定的一幕存档参与一幕场，但不能把三幕构筑降级挂到一幕场。
- 首期只做好友房间码对战，验证规则。公开匹配可以后续增加；不同时建设公会、商业化与League系统。
- 建议首先比较整回合交替与单动作交替。整回合交替复用较多，但要测首回合爆发和长连招；单动作交替的应对机会多，需要重新确定布防、状态持续和回合边界，不能作为小改动混入原PvE。
- 第一版可以优先评估整回合交替：各自回合开始重置行动点、清除自身旧布防并抽牌；自身回合结束处理弃牌与回合末效果，然后交给真人对手。敌方脚本不得继续执行。能力部署持续本场，状态的生效与递减必须逐类写清楚。
- 真人手牌和未来动作不可当作PvE意图直接展示。展示范围先限定为双方资源、状态、已出牌和公共弃牌信息；是否公开完整牌表另行决定。
- 随机先后手只能在大量对局中平摊先手优势，不等于消除单场优势。后手补偿、回合时间和动作次数的规则要经过对局验证，当前不填任意数字。

## 平衡边界

同幕匹配解决的是成长阶段差距，不能自动消除路线、精英奖励、升级次数、最大血量、遗物组合、重复刷图挑极品等差异。这些差异既是构筑的来源，也可能形成极端强度，不能简单抹平成统一牌组或统一血量。最大血量与卡组质量的取舍应保留；若某种成长选项过强，评估其获取成本、替代选项和完整构筑表现，而非在竞技入口直接删除该收益。

要专项测试先手击杀、无限抽牌或费用循环、长期限制对手行动、防守拖局、诅咒开局方差与版本兼容。先识别实际存在的组合，不预先宣称当前引擎已存在所有漏洞。必要的竞技专用限制或卡牌效果必须在入场前说明，并与PvE版本隔离。

测试除了胜率，也记录先后手、幕数、构筑类型、回合数、双方实际行动机会与对局耗时。不能单凭AI镜像对打宣称验证了真人博弈平衡。

## 工程边界与最小实现顺序

现有server.mjs只提供静态GET/HEAD，存档在浏览器localStorage，没有房间、数据库或服务器战斗状态。当前act/replay的纯规则结构可复用部分卡牌结算；PvE敌方脚本不能直接视为第二个玩家。

1. 历史卡组库：准确结算节点、幂等追加、不可变构筑、跨局列表与导出导入。将currentRun、deckArchive、pvpMatch作为三个不同生命周期的数据集合，禁止用当前局存档键同时保存全部历史。导入文件只算未验证存档。验收必须覆盖开新局、放弃、失败、通关和PvP结束后仍可找到并使用旧卡组；若仅本机保存，要说明清除浏览器数据不在保存保证内，不把本地存储说成云端备份。
2. 独立双人战斗规则：先用两份存档验证双方回合、状态生命周期、胜负和恢复，再连接房间。
3. 好友房间：持久保存房间与动作，由服务器校验回合、费用、目标与版本；只向各玩家发送自己的私有信息。先不做排行榜和奖励经济。
4. 正式竞技资格：服务器核验受控开局与完整行动记录，或由可信服务端产生存档。结构校验、客户端哈希、签名、截图和自报完成幕数，都不能单独证明通关合法。首期未验证存档要明确标注，不混入可信竞技池。

对局洗牌使用服务器控制的独立随机源，不复用公开PvE种子，不把共同种子发送给双方客户端。使用同一种洗牌算法是对称规则，双方牌表不同，不要求抽到同样的牌。随机算法可以复用，但随机状态与访问权限必须隔离。

当前observe()隐藏部分PvE信息，但仍含单机完整战况与日志，不能原样作为PvP对手视图。重连、重复请求、房间成员校验、超时和退出规则是房间最小实现的一部分。
